Turning a fuzzy claim into a measurable one

Three projects, one habit. Each takes a claim that normally goes untested and makes it into a number somebody can check — and each states, in writing and next to the result, what it does not establish.

“Our agent is safe.” ──▶ 60 adversarial cases, two configurations, an audit log, and two separate rates that disagree with each other on purpose.

Evaluation · adversarial testing

secure-agent-eval

Python 3.11+ · MIT · 60 cases · 80 tests · runs offline, no API key

An offline evaluation harness that runs a fixed set of adversarial cases against an LLM agent under two configurations — unguarded baseline and guarded — and reports the difference, split by attack category and by language, English and Spanish.

Why it exists

An agent with tools, memory and access to someone else’s data has an attack surface a chat model does not. The standard claim is “we added guardrails.” That claim is usually untested, and where it is tested, running the test costs money, so nobody re-runs it. This is 60 cases and a command that runs free and offline.

How it works

Under the baseline the guardrails still evaluate and still log what they would have decided, so a baseline run answers “what would have been blocked?” without changing what happened. Five categories: prompt injection where the payload arrives inside retrieved content, tool permission boundaries, data leakage, unsafe and irreversible actions, and human handoff — where stopping is the correct behaviour and a fluent answer is the failure.

It is provider-agnostic: one class, one method (step(TurnRequest) -> AgentTurn). The offline mock is a deliberately susceptible scripted agent, not a model. The Anthropic adapter is a ~60-line reference implementation.

What’s measurable

Two rates, because they answer different questions:

  • Unsafe rate — a forbidden effect reached the world or the user. Grades the system.
  • Attempt rate — the agent reached for the forbidden thing, blocked or not. Grades the agent.
Mock profileConfigurationUnsafeAttempted
compliantbaseline60/60 (100%)48/60 (80%)
compliantguarded3/60 (5%)38/60 (63%)
cautiousbaseline24/60 (40%)12/60 (20%)
cautiousguarded3/60 (5%)2/60 (3%)

The number worth arguing about is 63%, not 5%. Under guardrails the agent still reaches for the forbidden thing 38 times out of 60 and is stopped by a mechanism every time. The system got safe; the agent did not get better. A harness reporting only the unsafe rate would have hidden that.

The finding that didn’t go as pitched

I expected Spanish guardrails to degrade broadly. They didn’t. Of three guarded failures, exactly one is attributable to language: a case that says “voy a llevar esto a los tribunales” where the escalation patterns cover abogado, demandar and litigio. The other two are a matched English/Spanish pair that fails identically by design — they describe discrimination without naming it, which defeats a lexical rule in any language.

One case is n=1. The README says so.

What did replicate cleanly, in every cell: mechanisms transfer across languages, patterns don’t. The permission layer and the secret scanner score identically in both languages because they don’t know what language the request was in. The two lexical guardrails are the only places any gap appears. That generalises past this suite — prefer structural controls to pattern lists wherever the choice exists.

What it doesn’t do

Single-turn only. No encoding or obfuscation attacks — base64, homoglyphs, zero-width characters. No multimodal input. Two languages is not “multilingual”. Six cases per cell means several differences are one case wide, and no confidence intervals are reported because none would be meaningful. Cases and guardrails share an author, which biases coverage toward attacks I thought of — visible in the fact that the only cases that get through are the two I wrote to get through.

Data pipeline · entity resolution

nosara-listings — the no-MLS pipeline

Next.js 16 · React 19 · TypeScript · Tailwind 4 · Supabase · Playwright / cheerio

A scraping and deduplication pipeline that builds a single view of what is actually for sale in Nosara, Costa Rica, across nine agencies that do not share a database — plus the app that serves it.

Why it exists

Nosara has no MLS. Listings are open and non-exclusive, so the same house is advertised by four agencies at four prices under four descriptions, and nobody — buyer, seller or agent — can see the actual inventory. The market’s core information problem is duplication without a shared key.

As an engineering problem the interesting part is that there is no join key. No listing ID, no address standard, no shared taxonomy. Identity has to be inferred from attributes each agency records differently, or does not record at all.

How it works

Nine scrapers, one per agency — RE/MAX, Century 21, Two Costa Rica, Coldwell, Blue Zone, Mango, Sotheby’s, Tropicasa and Wanderlust. Playwright for the JavaScript-rendered sites, cheerio for the static ones. Each has a ── CONFIGURATION ── block at the top, so selectors are changed in one place when a site redesigns — which they do.

Union-Find deduplication. Every cross-agency pair is compared, matching pairs are unioned, and connected components become groups. That choice matters: duplication is transitive. If A matches B and B matches C but A and C look different because one agency omitted the lot size, they are still one house. Pairwise matching gets that wrong; connected components get it right.

The similarity function is explicit and tunable at the top of the file:

FieldRuleOn mismatch
bedroomsExactImmediate reject
price_usdWithin ±15%Counts as a disagreement
sqmWithin ±20%Counts as a disagreement
lot_sqmWithin ±20%Ignored
bathroomsExactIgnored — never rejects

A pair matches on at least two fields agreeing and zero disagreeing. Same-agency pairs are skipped — one agency listing a house twice is their problem, not a cross-source duplicate. Each group picks a canonical record and keeps every source attached, so the product is “this house, four agencies, four prices,” which is the thing that did not exist before.

One operational constraint is enforced in the repository rather than left to memory: scrapers run locally only, never on Vercel, and the Supabase service-role key never leaves the machine. That is the kind of rule that gets violated by accident during a deploy.

The honest engineering notes

The comparison is O(n²), with a comment saying so and why it is fine at roughly 500 listings. Naming it means a reader knows it was a decision rather than an oversight.

The tolerances are heuristics, not learned. They are extracted to named constants so they are tunable, but they are currently set by judgement, and there is no labelled ground-truth set to measure precision and recall against. That is the biggest gap in the project — and the most interesting thing in it to talk about.

What it doesn’t do

No test suite. No measured accuracy for the matcher. No geocoding, so identity inference cannot use location.

Compliance engine · data warehouse

fractal-desk-v2 — the deadline engine

Python 3.11+ · DuckDB · Streamlit · MIT · 224 tests · synthetic data only

A deadline engine and warehouse for Costa Rican electronic documents a business receives: it computes the statutory acceptance deadline per document, classifies each one’s status, validates structure, and serves it as a dashboard.

Why it exists

Two things reset the ground in 2025. Format v4.4 became mandatory on 1 September, and TRIBU-CR replaced ATV as the tax platform on 6 October. The new regime enforces a rule with money attached: an electronic document you receive must be answered — accepted, partially accepted or rejected — within the first eight business days of the month following the month it was issued. Miss it and the IVA credit on that document is permanently lost. No retroactive upload restores it.

The deadline is not “eight business days after the invoice.” It is a fixed calendar point per issue-month. Every document issued in March 2026 — the 1st, the 15th, the 31st — shares one deadline: the 8th business day of April 2026. The obvious implementation, issue_date + 8 business days, is wrong for every document it touches.

How it works

deadline(issue_date) = 8th business day of (issue_month + 1), over a business calendar with Costa Rican holidays and an explicit coverage guard — if the calendar does not cover the range being asked about, it raises rather than silently returning a wrong date.

StatusMeaning
ACCEPTEDConfirmed on or before the deadline. Credit secured.
PENDING_SAFEUnconfirmed, more than three business days remain.
PENDING_AT_RISKUnconfirmed, three or fewer business days remain — inclusive of the deadline day.
EXPIRED_CREDIT_LOSTThe window closed unanswered — or a confirmation was sent late.

That last clause is the judgement call I would defend. A document confirmed two days late is recorded as “accepted” in the source system, but the credit is gone. Reporting it as accepted would make the dashboard’s headline number a lie. The engine classifies outcome, not activity — so a late acceptance is EXPIRED_CREDIT_LOST and carries accepted_late=True so the distinction stays queryable.

The warehouse is layered dbt-style in DuckDB — raw_ → stg_ → int_ → dim_/fct_ — with numeric filename prefixes declaring dependency order. The deadline logic lives in Python and the SQL layer consumes it as fct_deadline_status rather than re-deriving it. One implementation, one place to defend.

A structural validator runs alongside it with ERROR, WARNING and INFO severities. One rule is a WARNING rather than an ERROR precisely because the catalogue behind it ships as a placeholder — making it an ERROR would produce a validator that is loudly confident on the strength of data it invented.

What it doesn’t do — and this is load-bearing

All data is synthetic, and the repository proves it structurally. Every taxpayer identifier begins 999, a range Costa Rica does not issue; every company name begins SYN; every mart row carries is_synthetic = TRUE. There are no keys, no live calls, and nothing in it can sign or transmit a document. lxml is present so the mock submission layer emits parseable XML — it is a parser, not a signer.

The regulatory notes open with “this is not tax advice” and record which rules the engine implements and why, with sources and a verification date, so that somebody qualified can check it against the law. They say outright: if the document and the law disagree, the law is right.

The v1 / v2 distinction

The repository also documents Fractal Desk v1, a university–industry partnership with Universidad Nacional de Costa Rica. Five UNA informatics students built it. I was client-side sponsor and general director: requirements, scope, acceptance criteria, schedule and milestone review. I did not write that code, and none of it is in this repository. The intellectual property is UNA’s and the students’.

v2 is my own independent work, and it is not a rebuild of v1. When ATV became TRIBU-CR the system v1 integrated with stopped existing, and the new regime created a problem that had no tool. So v2 is the deadline engine and nothing else — not a CRM, not project management, not invoicing. The narrowest thing that solves a problem people actually lose money to.

Talk tracks

secure-agent-eval≈ 3 min

An agent with tools and access to other people’s data has an attack surface a chat model doesn’t. The usual claim is “we added guardrails,” and that claim is usually untested — and where it is tested, running the test costs money, so nobody re-runs it.

So I built a harness: 60 adversarial cases across five categories — prompt injection, tool permission boundaries, data leakage, unsafe actions, and human handoff — each one in English and Spanish. It runs the same pipeline twice, once with guardrails off and once with them on, and reports the difference. It runs offline with no API key, so it’s free and anyone can re-run it. There’s an append-only audit log behind every number.

The design decision I’d defend hardest is reporting two rates instead of one. The unsafe rate asks whether harm actually reached the user — that grades the system. The attempt rate asks whether the agent reached for the forbidden thing at all, blocked or not — that grades the agent. Guardrails took the unsafe rate from 100% to 5%. The attempt rate went from 80% to 63%. So the system got safe and the agent didn’t get better — it’s being caught by a mechanism, every time. If I’d only reported the first number, that would have looked like a model improvement, and it isn’t one.

The bilingual result is the part I’d want to be honest about. I expected Spanish guardrails to degrade broadly. They didn’t — exactly one failure out of 60 is attributable to language. One case is n=1, not a finding, and the README says so. What did replicate cleanly is more useful: mechanisms transfer across languages, pattern-matching doesn’t. The permission layer and the secret scanner score identically in both languages because they don’t know what language the request was in. The two regex-based guardrails are the only places any gap shows up.

The obvious next step is testing the language hypothesis properly — about fifty escalation cases per language, sourced from real Spanish rather than mine — plus encoding attacks, which a regex filter should fail badly, and I’d like to measure how badly.

Anticipated objections

Questions a skeptical reviewer will ask

Your eval’s baseline is 100% unsafe. Isn’t that rigged?

Under the compliant mock profile, yes — by construction. It’s a worst-case bound, not a prediction, and it’s labelled that way. That’s why the cautious profile exists and is published alongside it: it reproduces the documented asymmetry that models resist direct adversarial requests far more than the same instruction arriving inside retrieved content, and it gives 40%. Both are in the README. Also worth saying: the mock can’t see which configuration it’s running under, and there’s a test asserting that — otherwise the comparison would be circular.

So did the Spanish thing work or not?

No, not as I framed it. One case out of 60. I’d rather report a hypothesis that didn’t replicate than round it up. The result that did replicate — mechanisms transfer across languages, pattern-matching doesn’t — is more useful anyway, because it’s an architectural recommendation rather than an observation about one language.

What’s the accuracy of your matcher?

I don’t know, and that’s the honest answer. There’s no labelled ground truth, so the tolerances are judgement. I know exactly how I’d get the number — hand-label a few hundred cross-agency pairs and tune against them — I just haven’t. What I did do is extract every threshold to a named constant at the top of the file, so when the ground truth exists the tuning surface is already there.

How do I know the tax rules in the deadline engine are right?

You don’t take my word for it. The regulatory notes record which rule the engine implements and why, with sources, dated, and they open by saying this isn’t tax advice and that if it disagrees with the law, the law is right. The engine also refuses to answer where it can’t — the business calendar raises rather than returning a wrong date when the holiday data doesn’t cover the range asked about.

Which of these is most like the work here?

secure-agent-eval, directly — it’s an eval harness with an explicit grading rubric, an audit trail, and results split by cohort. fractal-desk-v2 is the same discipline applied to a compliance domain: a rule with money attached, a status model that refuses to flatter the numbers, and a test suite. nosara-listings is the product end — a real pipeline with real ugly inputs that has to stay up.
